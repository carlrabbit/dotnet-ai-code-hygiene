### D. Correction amendment — collection-expression eligibility after experiment #14

**Observed on 2026-11-22:** After the SDK-restore and layout fixes, the raw [NuGet-content Draft PR #14](https://github.com/carlrabbit/dotnet-nuget-content/pull/14) preserved NuGet imports and converged in one pass, but a diagnostic build of a baseline-compiling project failed at three `foreach` sources. In `Program.cs`, the original `foreach (var name in new[] { "added", "modified", "deleted" })` and `foreach (var list in new[] { h.Changes.Added, h.Changes.Modified, h.Changes.Deleted })` became `foreach (... in [ ... ])`. `ProjectWorkspace.cs` similarly converted `foreach (var p in new[] { "alias", "packageId", "version", "packageFile", "directory" })`. **A `foreach` source is not itself a target-type context for a collection expression**; the resulting expressions have no target type and trigger `CS9176`. The current `CSharpCanonicalizer` checks `HasUntargetedVar`, but that does not cover such `foreach` sources.

- Correct collection-expression **eligibility**, not the generated target by hand. `new[]`, explicit array creation, and list/object collection-creation conversions must not emit `[...]` when the enclosing use provides no valid collection-expression target type. This includes the three observed `foreach` contexts and other directly comparable untargeted uses. Preserve the original creation syntax instead.
- Preserve intentionally supported conversions where a valid contextual target is established, including explicitly typed locals, fields/properties, method returns and the approved `IReadOnlyList<T>` case; M0027 deliberately permits changes to the concrete implementation of such a collection. A literal `foreach` special case alone is insufficient if another untyped context can produce the same error. Use inexpensive syntax-context inspection or existing SDK/Roslyn facilities; **do not introduce a general-purpose semantic-analysis/build gate, type inference framework, or new modernization family**.
- The M0029 repair should be verified by **one focused, fast deterministic regression** that contrasts the three ineligible `foreach` shapes with representative eligible typed conversions. Use the existing relevant test project; no new real SDK-project fixture, test suite, or release gate is needed for this correction.
- Re-run corrected Autoformat from source on a fresh disposable checkout of the **original target baseline** `25b28310c7de04426de02e4ac8037b32ed9dbd9e` with the already accepted Autoformat policy. Keep existing target [Draft PR #14](https://github.com/carlrabbit/dotnet-nuget-content/pull/14) as the comparison surface: append an ordinary commit containing **only the raw regenerated formatter output relative to the prior output**, without force-pushing, rewriting the first two experiment commits, hand-editing source, or changing target `main`. Preserve original Draft PR #13 unchanged. Do **not** open a third target PR by default.
- Compare generated source to the original target and the prior PR #14 output; confirm all three reported `CS9176` sites are fixed by a focused diagnostic build. Confirm required imports remain, one-pass convergence remains, and read-only check modes are clean. If other unrelated source failures remain, report their exact cause and keep the PR marked **DO NOT MERGE**; do not scope-creep into wholesale compile/semantic repair.
